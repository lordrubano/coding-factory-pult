## 3. Отрицательный контроль: четыре из семи

```
MUT-PULT-BUILD-FAILURE-AS-OK        KILLED   отказ сборки не выдаётся за успех
MUT-PULT-BUILD-EXTRA-FILE           KILLED   лишний файл в дереве ловится
MUT-PULT-WRITES-INTO-REPOSITORY     KILLED   запись в рабочее дерево запрещена
MUT-PULT-FAILURE-EXIT-AS-SUCCESS    KILLED   отказ не помечается нулевым кодом
```

**Три спецификации отложены — стенд не умеет работать с нецелевыми языками.**

```
MUT-PULT-ALLOWLIST-CHECK-SKIPPED    MUTATION_BROKE_SYNTAX, строка 74
MUT-PULT-PRIVATE-PROBE-REMOVED      MUTATION_BROKE_SYNTAX, строка 74
MUT-PULT-WIDE-KEY-TOLERATED         MUTATION_BROKE_SYNTAX, строка 74
```

Причина установлена чтением стенда: `scripts/cf_mutate.py` перед прогоном теста
безусловно вызывает `ast.parse` на мутированном файле — то есть разбирает **любую**
цель как код на Python. YAML разобран быть не может, и мутация объявляется
сломавшей синтаксис, не доходя до теста.

Следствие: три предохранителя публикации — порядок пробы ключа, обязательность
проверки списка перед отправкой, остановка при слишком широком ключе — **проверены
случаем, но не доказаны приманкой стенда**. По правилу отрицательного контроля это
непокрытые свойства.

Три спецификации сняты с реестра и сохранены вне его: оставленные, они держали бы
стенд красным по причине, к продукту отношения не имеющей. Реестр 342 → 339.

Предлагаемое устранение — отдельным шагом: разбор `ast.parse` применяется только
к целям с расширением `.py`; для прочих целей проверка синтаксиса не производится,
и исход определяется тестом.

## 4. Найденная недостача в рабочем процессе

Адрес открытого хранилища читается из переменной `CF_PULT_PUBLIC_REPOSITORY`,
которая не заведена. Проверка `test -n` остановит запуск на втором шаге. Обнаружено
чтением файла, не прогоном: сеть исполнителю запрещена, первый настоящий запуск —
за владельцем.

## 5. Что неизвестно

- Рабочий ли ключ в секрете. Доказывается первой публикацией: прошла — рабочий,
  встала — нет. Отдельной пробы владелец не назначил, и правильно: двух шагов там,
  где хватает одного, не делается.
- Ветка, которую создаст первая публикация в пустом открытом хранилище, заранее не
  известна: она зависит от `init.defaultBranch` бегунка. Включение Pages возможно
  только после её появления.
- Три свойства предохранителей — до починки стенда.
